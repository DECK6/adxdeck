AKM WEEK 03 / 학습 가이드 + 실행 워크북

그럴듯한 AI 초안을 ‘다시 써도 되는 지식’으로 바꾸는 자가검증 루프

AI가 만든 문장이 매끄럽고 형식이 정확해 보여도, 날짜·수치·조건·주체가 원문과 맞는지는 별개의 문제입니다. 더 자연스럽게 다시 쓰게 하는 것만으로는 사실 오류가 자동으로 사라지지 않으며, 전면 재작성은 오히려 원래 맞던 내용을 잃게 할 수 있습니다. 이 가이드는 AI 초안을 계속 고쳐 쓰는 법이 아니라 현재 초안의 무엇을 보존하고, 어떤 근거가 있을 때만 최소 수정하며, 언제 보류하거나 멈출지 결정하는 법을 설명합니다.

전체 학습 흐름은 문제 사례 → refinement와 verification의 구분 → 증거 독립성 → 방법 선택 → 유한한 검증 루프 → 수정 후 판정 → 과검증 위험 → Tier와 중단 규칙 → 두 가지 실습으로 이어집니다. 표와 카드는 비교와 회상을 돕지만, 각 표 앞뒤의 설명과 해석까지 읽어야 실제 작업에 적용할 수 있습니다.

GUIDE / 학습 약속

이 가이드를 사용하는 사람과 학습 약속

AI 채팅을 이제 막 쓰기 시작한 사람, Obsidian·Notion·문서 폴더 같은 PKM을 이미 운영하는 사람, 파일 에이전트에게 작업을 맡기지만 검증과 Learn Back을 아직 체계화하지 않은 사람 모두를 대상으로 합니다. 특정 앱, 데이터베이스나 에이전트 런타임 설치는 필요하지 않습니다. 화면에서 이 문서를 읽고, 제공된 가상 자료를 복사할 수 있으면 됩니다.

모든 사례는 완전한 허구이며 실제 기관·사람·일정·승인·성과를 나타내지 않습니다. 실습에는 실제 개인정보, 비공개 대화, 계정 정보, 인증값이나 내부 로그를 넣지 않습니다. 외부 source나 도구에 접근하지 않았다면 접근했다고 주장하지 않고, 실행하지 않은 hash나 readback을 증거로 꾸미지 않습니다.

이 가이드를 마치면 다음을 할 수 있어야 합니다.

  1. refinement(다듬기)와 verification(검증)을 구분합니다.
  2. DEER와 KSI를 논문 열 편과 다른 층위의 AKM 적용 렌즈로 설명합니다.
  3. 같은 모델의 비평부터 직접 원문·결정적 검사·책임 있는 사람의 경계까지 증거 독립성의 차이를 판단합니다.
  4. baseline freeze → 독립 질문 → 직접 증거 → correction gate → no-degradation → 판정 → 조건부 Learn Back 순서를 적용합니다.
  5. 검증 반복이 새 오류·비용·잘못된 규칙을 누적할 수 있는 이유와 명시적 중단 규칙을 설명합니다.
  6. 일반 채팅 모델과 파일 에이전트에 맞는 두 과제를 다른 문서 없이 실행하고 판정합니다.

학습을 마칠 때 다음 문장을 자신의 작업에 맞게 완성합니다.

“내 작업은 [위험 Tier]이고, [가장 독립적인 증거]가 없으면 [고치지 않기/HOLD/사람에게 이관]하겠다.”

먼저 AI 초안이 정확한 문장처럼 보이면서도 날짜·수치·조건을 어떻게 바꿀 수 있는지, 그리고 왜 맞는 정보까지 함께 보존해야 하는지 살펴봅니다.

01 / 가상 오류 사례

이 사례를 풀려면 표현을 개선하는 일과 사실을 바꿀 권한을 심사하는 일을 먼저 분리해야 합니다.

02 / REFINE ≠ VERIFY

2. Refinement와 Verification은 다른 활동이다

이 구분이 필요한 이유는 AI에게 “검토해 줘”라고 말했을 때 표현 개선과 사실 판정이 한 응답 안에서 섞이기 쉽기 때문입니다. 두 활동을 분리하지 않으면 자연스러운 새 문장이 강한 근거처럼 보이고, 근거가 없는 수정까지 개선으로 오인할 수 있습니다.

Refinement는 문체, 구조, 길이, 제약 준수와 설명 순서를 개선해 더 나은 후보를 만드는 활동입니다. 같은 모델이 자기 답을 비평하고 다시 쓰는 방식도 포함됩니다. 낮은 위험의 표현 교정에는 값싸고 유용할 수 있지만, 비평자와 작성자가 같은 지식·편향·문맥을 공유하면 같은 사실 오류를 자신 있게 반복할 수 있습니다.

Verification은 새로운 답 하나를 더 만드는 활동이 아니라, baseline을 바꿀 권한이 있는지 심사하는 증거 절차입니다. 초안 전에 기준을 고정하고, 판정을 바꿀 claim을 질문으로 분리하고, 그 질문을 원문·도구·환경 출력·결정적 검사에 연결합니다. 근거가 구체적인 충돌이나 필수 기준 실패를 보여 줄 때만 최소 수정하며, 근거가 없으면 보존·주석·HOLD 중 하나로 멈춥니다.

구분 주된 목적 유용한 장면 단독으로 맡기면 안 되는 것 종료 기준
Refinement 더 읽기 좋고 제약을 잘 지키는 후보 만들기 문체, 구조, 길이, 설명 순서 사실 확정과 고영향 변경 승인 요청한 표현 개선이 끝나면 종료
Verification 보존·수정·보류를 증거로 결정하기 날짜, 수치, 주체, 성과, 요구사항, 안전 경계 근거 없는 전면 재작성 판정과 중단 조건이 명시되면 종료

실제 작업에서는 다음 여섯 질문으로 두 활동이 섞였는지 점검합니다.

  • 검사 기준이 초안 전에 고정되었는가?
  • 질문이 초안 문구에 끌리지 않도록 원자 claim으로 분리되었는가?
  • 답이 원문·도구·환경·결정적 검사에 연결되는가?
  • 증거가 실제로 baseline과 충돌하는가?
  • 수정 후 요청 적합성·맞던 사실·형식·안전 경계가 나빠지지 않았는가?
  • 근거가 없을 때 바꾸지 않고 멈출 수 있는가?

따라서 refinement 결과는 검증할 후보이고, verification 결과는 그 후보를 유지·수정·보류하는 결정입니다. 두 활동의 차이를 알았다면 다음에는 어떤 근거가 초안과 같은 오류를 공유하고, 어떤 근거가 그 오류에서 더 멀어지는지 봐야 합니다.

03 / 증거 독립성

3. 증거 독립성 사다리

검증 질문을 만들었다고 곧바로 사실을 확인한 것은 아닙니다. 같은 모델의 자기비평, 여러 샘플, 다른 모델의 판정, 검색 결과, 직접 원문과 결정적 검사는 서로 다른 오류를 줄입니다. 이 차이를 모르고 모두를 “확인”이라고 부르면 약한 신호가 수정 권한으로 과대 승격됩니다.

아래 사다리는 절대 진리의 서열이 아니라, 각 증거 표면이 초안의 공통 오류와 어느 정도 분리되는지를 보는 실무 도구입니다. 낮은 단계는 질문 생성과 우선순위 결정에 유용하고, 높은 단계는 사실 수정·고영향 공개·책임 경계를 강화합니다.

단계 증거 표면 줄이는 오류 남는 한계 AKM에서 맡길 역할
1 같은 모델의 자기 비평 표현 누락·제약 위반을 발견할 수 있음 같은 지식·편향·초안 고정효과 질문 후보와 낮은 위험 refinement
2 같은 모델의 독립 샘플 여러 개 한 번의 우연한 생성에 덜 의존 공통 오류가 일관되면 모두 틀릴 수 있음 불확실성·불일치 신호
3 초안을 숨긴 독립 verification questions 초안 문구 복제와 결합을 줄임 같은 모델 지식의 한계는 남음 확인할 claim 분해
4 다른 모델 verifier 또는 judge 자기확증을 일부 줄임 약한 judge, 보정 오류, prompt 민감성 보조 판정과 disagreement 신호
5 retrieval로 회수한 외부 자료 모델 내부 지식만 쓰는 상태에서 벗어남 검색 순위·요약·낡은 페이지는 권위가 아님 원문 후보 탐색
6 권위 있는 원문 직접 읽기, 도구·환경 출력 claim과 외부 현실을 직접 대조 출처 자체의 오류·범위·시점 한계 사실 수정의 우선 근거
7 고정된 수용 기준에 대한 deterministic check 모호한 채점을 줄이고 재현 가능 검사에 쓰인 규칙만 확인함 파일·구문·수치·테스트·해시 검증
8 책임 있는 사람·도메인 권한자의 검토와 승인 가치 판단·안전·법적 책임의 공백을 메움 사람도 틀릴 수 있어 근거 기록 필요 고영향 공개·안전·예외의 최종 책임 경계

이 표를 읽을 때 핵심은 한 단계 위가 모든 문제에서 무조건 옳다는 뜻이 아니라는 점입니다. 같은 모델의 critique와 sampling은 누락이나 불일치를 발견할 수 있지만 사실을 증명하지 않습니다. 다른 모델 judge도 자기확증을 일부 줄일 뿐, 약한 판정기와 prompt 민감성을 남깁니다. Retrieval은 원문 후보를 찾는 단계이며 검색 순위나 요약 자체가 권위는 아닙니다.

권위·범위·시점을 확인한 직접 원문, 실제 도구·환경 출력과 고정 기준의 deterministic check는 수정 권한을 강화합니다. 그러나 결정적 검사도 구현한 규칙만 확인하고, 사람 승인도 무오류를 뜻하지 않습니다. 고영향 작업에서는 근거 기록과 책임 있는 권한 경계를 함께 남깁니다.

이 사다리는 하나의 만능 방법을 고르는 표가 아닙니다. 이제 각 연구 방법이 질문 생성, 외부 확인, 보수적 수정, 판정 한계 중 어디를 담당하는지 비교할 수 있습니다.

04 / 2 LENSES + 10 METHODS

4. AKM 적용 렌즈 2개와 버전 고정 논문 방법론 10개

방법을 비교하는 이유는 최신 기법의 이름을 외우기 위해서가 아니라, 현재 작업에서 어떤 메커니즘을 어디까지 믿고 어떤 경계와 함께 사용할지 결정하기 위해서입니다. 같은 “자가검증”이라는 이름 아래에도 표현 개선, task feedback 기억, 독립 질문, 외부 도구, retrieval, sampled consistency, 보수적 correction gate와 judge 신뢰도 평가가 섞여 있습니다.

이 비교 표면은 정확히 12개 행입니다. 그러나 논문 12편이 아닙니다. DEER와 KSI는 AKM 적용 렌즈 2개이고, 나머지는 버전이 고정된 논문 방법론 10개입니다.

  • DEER는 한 산출물을 여러 품질 차원에서 평가하고, 작업 위험에 따라 검증 깊이를 정하는 AKM 렌즈입니다.
  • KSI는 여러 작업의 경험을 적용 조건이 있는 candidate로 만들고, 반복·반증·held-out·cross-model transfer evidence 전에는 승격하지 않는 Learn Back 렌즈입니다.
  • 논문 열 편은 refinement, verification, correction, sampling과 judge 한계를 비교하기 위한 별도의 corpus입니다.

표를 실제 결정에 사용할 때는 방법 이름보다 evidence source와 baseline 보존 열을 먼저 봅니다. Self-Refine과 Reflexion은 내부 feedback을 이용한 표현 개선과 제한된 기억에 유용하지만 사실 판정 권한은 아닙니다. Huang et al.은 외부 feedback이 없는 intrinsic correction이 개선을 보장하지 않음을 경고합니다.

CRITIC은 도구가 실제로 판정할 수 있는 작업에서 외부 feedback을 사용하고, Chain-of-Verification은 초안을 숨긴 질문으로 결합을 줄입니다. RARR은 retrieval evidence와 baseline의 disagreement가 있을 때만 최소 수정하며, SelfCheckGPT는 여러 샘플의 일관성을 불확실성 신호로 사용합니다. 이 네 방법도 각각 도구 권위, 같은 모델 지식, retrieval 최신성, 공동 오류라는 한계를 남깁니다.

SkillAxe, DISC와 RuVerBench는 baseline 비교, degradation, correction gate와 judge noise를 더 직접적으로 보여 줍니다. 세 논문은 2026년 preprint이며, 해당 논문의 benchmark 결과를 현재 AKM·학습자·조직의 성과로 옮겨 말할 수 없습니다. DEER와 KSI 역시 모든 benchmark나 runtime을 복제하라는 뜻이 아니라, 평가 깊이와 승격 경계를 조직하는 렌즈로만 사용합니다.

05 / ONE BOUNDED CYCLE

5. 한 번의 보수적 검증 루프

방법론 비교를 실제 행동으로 바꾸려면 시작과 종료가 분명한 절차가 필요합니다. 무한한 자기비평 대신 한 cycle 안에서 baseline, 질문, 증거, 수정, readback과 판정을 모두 남기면 맞던 답을 지키면서도 중요한 오류를 고칠 수 있습니다.

아래 여덟 단계는 각각 왜 필요한가 → 무엇을 하는가 → 어떤 evidence를 남기는가로 읽습니다. 단계 이름만 체크하는 것으로는 충분하지 않습니다.

1. Baseline freeze

  • 왜 필요한가: 원본이 없으면 수정 후 무엇이 좋아지고 나빠졌는지 비교할 수 없습니다. 전면 재작성 중 맞던 claim이 사라져도 발견하기 어렵습니다.
  • 행동: 초안 원문, 목적, 독자, 필수 항목과 금지 항목을 변경 없이 보존합니다. 채팅은 초안을 그대로 BASELINE_FROZEN에 복사하고, 파일은 원본 artifact를 별도로 유지합니다.
  • evidence: 동결한 초안이나 baseline artifact와 식별자를 남깁니다. SHA-256은 실제 deterministic hash tool을 실행한 파일에만 기록하며, 채팅만으로 계산했다고 주장하지 않습니다.

2. 고영향 범위 선택

  • 왜 필요한가: 모든 문장을 검사하려 하면 critique noise와 비용이 커지고 완료 기준이 사라집니다.
  • 행동: 날짜·수치·기관·주체·성과·안전·요구사항 가운데 결과 판정을 바꿀 3–5개 claim만 고릅니다.
  • evidence: 선택한 claim 목록과 각 claim이 틀렸을 때 생기는 영향 또는 연결된 수용 기준을 남깁니다.

3. 독립 질문 설계

  • 왜 필요한가: 초안 문장을 그대로 묻으면 모델이 표현을 복제하며 같은 결론에 고정될 수 있습니다.
  • 행동: “원문이 말하는 운영 요일은?”, “정원은?”, “장비 요구가 명시됐는가?”처럼 답이 짧고 반증 가능한 원자 질문을 만듭니다. 초안의 결론을 질문 안에 넣지 않습니다.
  • evidence: verdict를 바꿀 수 있는 질문 3–5개와 각 질문이 확인하는 기준을 남깁니다.

4. 초안과 분리해 답하기

  • 왜 필요한가: 질문과 답을 초안에서 분리할수록 초기 문구의 결합과 자기확증을 줄일 수 있습니다.
  • 행동: 가능하면 초안을 보여 주지 않고 source packet·도구·환경에 질문합니다. 같은 채팅 안에서 같은 모델이 답하면 완전 독립이 아니라는 한계를 명시합니다.
  • evidence: 질문별 source-only answer, verifier identity, 초안 노출 여부와 independence limit을 기록합니다.

5. Evidence priority 적용

  • 왜 필요한가: critique, 다수 샘플, 다른 모델 판정은 유용한 신호이지만 사실 수정의 최종 근거가 아닙니다.
  • 행동: 권위 있는 원문 직접 읽기와 exact locator, 실제 tool/environment output, 고정 수용 기준의 deterministic check를 우선합니다. 고영향 승인에는 책임 있는 사람·도메인 권한자의 경계를 둡니다.
  • evidence: 각 답에 source locator, 도구 출력 또는 검사 결과를 연결하고, 접근하지 못한 단계는 사용했다고 쓰지 않습니다.

6. Correction gate

  • 왜 필요한가: 더 좋은 표현이라는 이유만으로 수정하면 false correction과 over-editing이 생깁니다.
  • 행동: evidence가 baseline과 구체적으로 충돌하거나 필수 기준 실패를 직접 지지할 때만 근거가 지목한 최소 범위를 고칩니다. Source가 말하지 않은 claim은 거짓으로 확대하지 않고 UNSUPPORTED로 낮춥니다.
  • evidence: 변경마다 baseline fragment, evidence-backed reason, exact locator와 minimal diff를 남깁니다. 근거가 없으면 NO_CHANGE 또는 HOLD입니다.

7. No-degradation readback

  • 왜 필요한가: 한 오류를 고치면서 맞던 정보·필수 섹션·형식·링크·안전 경계를 망가뜨릴 수 있습니다.
  • 행동: final을 직접 다시 읽고 baseline 및 수용 기준과 비교합니다. 목적 적합성, 맞던 claim, 필수 내용, 형식, 링크, 안전 경계와 새 unsupported claim을 확인합니다.
  • evidence: 전후 비교 결과, 실제 readback, 요청된 deterministic check와 발생한 regression을 기록합니다. baseline에서 PASS였던 항목이 final에서 FAIL이면 복원하거나 HOLD합니다.

8. Verdict와 조건부 Learn Back

  • 왜 필요한가: 종료 판정이 없으면 루프가 계속되고, 한 번의 우연한 성공이나 오판이 전역 규칙으로 전파될 수 있습니다.
  • 행동: PASS / PASS_WITH_NOTE / HOLD / FAIL 중 하나로 닫습니다. Learn Back은 적용 조건·비적용 조건·근거·반증 조건을 모두 가진 candidate일 때만 남깁니다.
  • evidence: verdict와 이유, correction cycle 수, stop condition, unresolved item, 필요한 HOLD 필드, candidate의 promotion boundary를 기록합니다.

이 루프의 품질은 단계 수를 오래 반복했는지가 아니라, baseline이 남아 있고 수정 권한이 강한 근거에 묶였으며 한 번의 readback과 명시적 판정으로 끝났는지에 달려 있습니다. 이제 같은 가상 공지에 정확히 한 cycle만 적용해 관계 판정과 최소 수정을 연결해 보겠습니다.

06 / WORKED EXAMPLE

6. Worked example — 가상 공지에 한 cycle 적용하기

Worked example이 필요한 이유는 “근거가 있을 때만 고친다”는 원칙을 실제 문장 관계로 바꾸기 위해서입니다. 독립 질문의 답은 baseline과 비교해 다음 세 가지 관계로 판정합니다.

관계 뜻 기본 행동
SUPPORT source가 baseline claim과 일치하거나 직접 지지함 그대로 보존
CONTRADICT source가 baseline과 구체적으로 충돌함 evidence가 지목한 최소 범위만 수정
UNSUPPORTED source가 그 claim을 지지하지 않지만 반대 사실까지 입증한 것은 아님 단정을 삭제·약화하거나 추가 근거 전까지 HOLD

UNSUPPORTED는 “거짓이 입증됨”과 다릅니다. Source 접근 자체가 없으면 INACCESSIBLE로 분리해야 합니다. 이 구분을 먼저 해야, 근거 부재를 반대 사실로 과장하지 않고 맞던 문장을 보존할 수 있습니다.

목적: 일정·마감·정원·준비물을 정확히 알리는 4문장 공지
Baseline: “봄빛도서관 글쓰기실은 화요일 18:00–20:00에 열립니다. 정원은 15명입니다. 월요일 18:00까지 신청하세요. 개인 노트북이 필수입니다.”
가상 원문: “청소년 글쓰기실: 수요일 18:00–20:00. 정원 12명. 신청 마감 월요일 18:00. 장비 안내는 별도 공지 예정.”

독립 질문 직접 근거의 답 baseline과 관계 조치
운영 요일·시간은? 수요일 18:00–20:00 화요일과 구체적 충돌 수요일로 최소 수정
정원은? 12명 15명과 구체적 충돌 12명으로 최소 수정
신청 마감은? 월요일 18:00 baseline과 일치 그대로 보존
개인 노트북이 필수인가? 원문에 필수라고 쓰지 않았고 장비는 별도 공지 예정 지원 부재 필수 단정 삭제, 별도 공지 예정으로 낮춤

한 번 수정한 최종본: “봄빛도서관 청소년 글쓰기실은 수요일 18:00–20:00에 열립니다. 정원은 12명입니다. 월요일 18:00까지 신청하세요. 장비 안내는 별도 공지 예정입니다.”

No-degradation readback: 네 문장, 일정·마감·정원·준비물 범위와 원래 맞았던 월요일 18:00 정보가 유지되었습니다. 새 기관·성과·비용·준비물 claim은 추가되지 않았습니다.

판정: PASS — 제공된 가상 원문 범위에서 모든 고영향 항목이 직접 지지되고, correction cycle 1/1 뒤 필수 정보 비열화가 없습니다.

조건부 Learn Back candidate: “일정 공지는 요일·시간·마감·정원·장비를 서로 다른 claim으로 검사한다.” 적용 조건은 구조화된 원문 안내가 있을 때, 비적용 조건은 원문이 없거나 일정이 실시간으로 바뀌는 경우, 근거는 이 가상 비교 기록, 반증 조건은 이 분해가 누락을 늘리는 경우입니다. 이 한 사례만으로 전역 규칙으로 승격하지 않습니다.

이 예시에서 핵심은 틀린 두 항목을 고친 것만이 아닙니다. SUPPORT인 마감을 의도적으로 지켰고, UNSUPPORTED인 장비 claim을 “틀렸다”고 과장하지 않았으며, 수정 뒤 네 문장의 역할을 다시 읽었습니다. 이 패턴은 일정뿐 아니라 수치·요구사항·성과·기관 claim을 다룰 때도 같은 방식으로 적용됩니다.

네 가지 판정과 다음 행동

판정 의미 다음 행동
PASS 적용한 검사와 필수 기준이 모두 통과 baseline·증거·최종본을 보존하고 종료
PASS_WITH_NOTE 사용할 수 있으나 낮은 위험의 충돌·범위·불확실성을 함께 남겨야 함 주석을 제거하지 말고 제한된 재사용
HOLD 중요한 근거·권한·범위 문제가 남아 수정이나 공개를 승인할 수 없음 부족한 증거, 책임자, 다음 확인 1개, 재개 조건을 기록하고 중단
FAIL 결과가 오해를 만들거나 필수 요구가 크게 빠져 작은 수정으로 회복하기 어려움 baseline을 보존하고 재작업 계약부터 다시 설정

한 번 잘 고친 사례가 있다고 해서 검증 반복을 늘릴수록 더 안전해지는 것은 아닙니다. 검증 자체가 새 질문·판정·수정문을 만들며 시스템 상태를 바꾸기 때문입니다.

07 / OVER-VERIFICATION

7. 과도한 검증이 실패를 누적하는 방식

이 내용을 따로 배워야 하는 이유는 검증이 수동적인 관찰이 아니기 때문입니다. 루프를 한 번 추가할 때마다 새 질문, 새 답, 새 judge 판정과 새 수정문이 생깁니다. 각 산출물은 다음 반복의 입력이 되고, 약한 critique 하나가 false correction을 거쳐 Learn Back 규칙으로 전파될 수 있습니다.

따라서 “더 많이 검증하면 단조롭게 안전해진다”는 가정은 성립하지 않을 수 있습니다. 검증의 목표는 흠을 무한히 찾는 것이 아니라, 위험에 비례한 질문과 근거로 유한한 결정을 만드는 것입니다.

실패 누적 방식 어떻게 쌓이는가 조기 신호 안전한 대응
False correction 맞던 baseline을 약한 반대 의견 때문에 틀리게 바꿈 수정 전 PASS가 수정 후 FAIL baseline 복원, 구체적 외부 근거 없으면 HOLD
Over-editing 한 claim 충돌을 고치며 문체·범위·다른 claim까지 불필요하게 재작성 diff가 근거가 가리킨 범위보다 큼 최소 수정, agreement/correction gate, 변경 이유 행별 기록
Critique noise 같은 모델이 매회 새로운 흠을 제안해 끝없는 할 일을 만듦 검사의 초점이 수용 기준 밖으로 이동 고영향 질문 3–5개로 동결, 낮은 위험 제안은 별도 backlog로도 만들지 않음
Weak-judge propagation 부정확한 judge 판정이 correction과 skill 규칙으로 재사용됨 judge끼리 불일치하거나 source와 반대 judge 신호를 보조로 낮추고 직접 source·deterministic·human authority로 이관
새 모순 생성 한 문장을 고친 뒤 다른 문장·표·요약과 충돌 매 반복마다 contradiction 수가 줄지 않고 위치만 이동 no-degradation readback 1회 후 새 중대 모순이면 루프 중단·HOLD
Token·시간 inflation sampling, retrieval, judge, rewrite가 반복될수록 본 작업보다 검증이 커짐 검증 시간이 작성·의사결정 시간보다 길어짐 위험 Tier를 낮추거나 범위를 줄이고 cap 도달 즉시 종료
Generic HOLD·backlog 불확실성을 전부 HOLD로 보내 책임 없는 대기열이 커짐 부족한 증거·담당·재개 조건이 없는 HOLD HOLD마다 결손 1개, 다음 확인 1개, 책임 경계, 재개/폐기 조건을 필수화
잘못된 규칙 학습 한 번의 우연한 실패나 judge 오판을 전역 절차로 Learn Back appliesWhen·falsifier·다른 task 증거가 없음 candidate로만 보존하고 반복·held-out·transfer gate 전에는 승격 금지

이 여덟 위험은 서로 연결됩니다. Critique noise가 불필요한 변경을 만들면 over-editing과 새 모순이 생기고, 이를 weak judge가 승인하면 false correction이 다음 규칙으로 전파될 수 있습니다. 반복 비용이 커지면 결정을 미루는 막연한 HOLD가 쌓이며, 결국 검증 시스템 자체가 본 작업보다 커집니다.

엄격한 gate도 설계가 나쁘면 실패합니다.

  • 기준이 너무 넓으면 반복마다 새로운 미세 결함이 발견되어 완료 상태가 사라집니다.
  • 기준이 모호하면 judge가 같은 산출물을 매번 다르게 평가하고 correction noise가 생깁니다.
  • 모든 불확실성을 같은 HOLD로 보내면 중요한 작업과 사소한 작업이 책임 없는 대기열에 섞입니다.
  • 수정 권한과 학습 권한을 섞으면 한 번의 false correction이 다음 작업의 instruction이 됩니다.
  • baseline과 공정한 비교 예산을 잃으면 더 많은 호출을 쓴 revised 조건을 개선으로 오해합니다.

좋은 검증은 오류를 끝없이 생산하는 비평 공장이 아니라, 어떤 근거가 수정 권한을 얻고 언제 멈추는지 정한 유한한 결정 절차입니다. 따라서 검증 강도는 반복 욕구가 아니라 작업 위험, 재사용 가치와 필요한 근거의 종류를 기준으로 정해야 합니다.

08 / TIER · STOP · HOLD

8. 위험 Tier, stop rule과 HOLD

모든 작업에 같은 검증 깊이를 적용하면 낮은 위험의 답은 불필요하게 느려지고, 높은 위험의 공개·안전·계약 작업은 충분한 권한과 근거 없이 처리될 수 있습니다. Tier는 모델 호출 횟수를 늘리는 등급이 아니라 작업 위험에 맞는 evidence, correction cap과 책임 경계를 선택하는 정책입니다.

아래 다섯 행은 저장 여부, 공개 영향, 고위험성, 반복 실패를 기준으로 필요한 검증과 실패 행동을 다르게 정합니다.

Tier 기본 trigger 필요한 검증 correction cap 실패 시 행동
Tier 0 Quick 저장하지 않는 낮은 위험의 짧은 답 필요한 exact lookup·tool check만, formal loop 없음 0 범위 축소 또는 불확실성 표시
Tier 1 Durable Note 다시 쓸 일반 노트·요약 source/readback/frontmatter, 고영향 claim이 있을 때만 제한 질문 최대 1회 근거 없는 rewrite 거부, 필요한 부분만 HOLD
Tier 2 Deep Report 공개 글·강의·제안서·중요 합성 7차원, Guidance, 고영향 질문 3–5개, 직접 근거, readback routine 최대 1회 미해결 claim을 낮추거나 HOLD하고 종료
Tier 3 High-stakes 안전·의료·법률·계약·공식 제출·고위험 공개 claim ledger, source authority, one-rubric focus, 사람 책임 경계 최대 2회 결정적·직접·권한 있는 근거 없이는 공개 금지·HOLD
반복 실패 같은 failure signature가 재발 prior baseline과 실패 조건 동결 후 Tier 2 또는 3 적용 최대 2회 같은 실패가 다시 나면 실행 중단, 절차 후보만 Learn Back

높은 Tier는 단순히 모델을 더 많이 호출하라는 뜻이 아닙니다. 더 직접적이고 결정적이며 권한 있는 근거를 요구하고, baseline·claim·책임 경계를 더 분명히 남기라는 뜻입니다. 낮은 Tier에서도 필요한 exact lookup이나 tool check는 생략하지 않으며, 높은 Tier에서도 근거 없는 반복은 허용하지 않습니다.

여섯 가지 stop rule

다음 중 하나면 더 많은 자기비평이나 새 rewrite를 요청하지 않고 즉시 멈춥니다.

  1. correction cap에 도달했습니다.
  2. 직접 source, tool/environment output, deterministic check나 책임 있는 human authority 가운데 필요한 결정 근거가 없습니다.
  3. 수정본이 baseline의 맞던 claim·필수 요구·안전 경계·형식을 중대하게 악화시켰습니다.
  4. judge가 불일치하지만 이를 해소할 더 강한 evidence가 없습니다.
  5. 한 번의 no-degradation readback 뒤 새로운 중대 모순이 생겼습니다.
  6. 검증 비용이 작업 위험과 재사용 가치에 비해 과도해졌습니다.

HOLD에 반드시 남길 네 필드

중단할 때는 baseline을 복원하거나 유지하고 HOLD를 붙입니다. HOLD는 막연한 대기 상태가 아니라 재개 가능성을 통제하는 판정이므로 다음 네 필드를 모두 적습니다.

  1. 부족한 증거: 지금 어떤 근거가 없어 결정을 승인할 수 없는가?
  2. 다음 확인 한 가지: 가장 먼저 수행할 구체적 확인은 무엇인가?
  3. 책임자 또는 권한 경계: 누가 확인·승인·예외 결정을 맡아야 하는가?
  4. 재개 조건: 어떤 evidence가 생기면 루프를 다시 열 수 있는가?

네 필드를 만들 수 없다면 범위를 줄여 PASS_WITH_NOTE로 사용할 수 있는지 검토합니다. 실제 사용이 오해를 만들거나 필수 요구가 크게 빠졌다면 FAIL로 닫습니다. 높은 판정이 항상 좋은 것이 아니라, 현재 근거와 사용 가능성을 가장 정직하게 표현한 판정이 좋은 판정입니다.

이제 자신의 작업에 적용할 문장을 채웁니다.

“내 작업은 [위험 Tier]이고, [가장 독립적인 증거]가 없으면 [고치지 않기/HOLD/사람에게 이관]하겠다.”

9. 과제 1 — 일반 채팅 모델에서 prompt-only 자가검증 루프 실행

파일 도구가 없는 일반 채팅에서도 검증의 핵심 구조를 연습할 수 있어야 합니다. 이 과제는 같은 대화 안의 모델 답이 완전히 독립적이지 않다는 한계를 숨기지 않으면서도, baseline 보존·source-only 답·최소 수정·한 번의 판정이라는 기본 습관을 익히기 위해 필요합니다. 아래 가상 자료와 전체 prompt를 사용하면 별도 문서 없이 절차를 실행하고 결과를 판정할 수 있습니다.

학습 목표

별도 에이전트나 파일 도구 없이도 baseline을 보존하고, 3–5개의 독립 질문, 직접 제공된 source 우선, correction gate, no-degradation, 유한 판정을 한 번의 채팅 응답으로 수행합니다.

개인정보 안전 가상 입력

이 예시는 실제 기관·사람·일정이 아닌 완전한 허구입니다.

  • 목적: ‘별모래 학습관’의 가상 토요 워크숍 안내 4문장을 정확하게 만들기
  • 초안: “워크숍은 9월 14일 일요일 오후 1시에 시작합니다. 정원은 20명입니다. 신청은 9월 12일 오후 6시까지입니다. 태블릿을 반드시 가져오세요.”
  • Source A: “별모래 학습관 가을 워크숍. 2026년 9월 12일 토요일 13:00–15:00. 정원 16명.”
  • Source B: “신청 마감: 2026년 9월 10일 목요일 18:00. 준비물은 추후 문자 안내.”
  • 수용 기준: 날짜·요일·시간·정원·마감·준비물을 4문장 안에서 구분하고, source에 없는 준비물을 단정하지 않기

PROMPT-ONLY SELF-VERIFICATION LOOP

[PROMPT START — PROMPT-ONLY SELF-VERIFICATION LOOP]

역할:
너는 초안을 무조건 다시 쓰는 편집자가 아니라, 증거가 있을 때만 baseline 변경을 허용하는 보수적 verifier다. 같은 모델의 자기비평은 사실 증명이 아니라 질문 후보라는 한계를 명시한다.

개인정보·보안 경계:
- 실제 개인정보, 비공개 대화, 계정 정보, 인증값, 내부 로그를 요구하거나 추론하지 않는다.
- 제공되지 않은 source를 읽었다고 주장하지 않는다.
- 외부 원문이나 도구에 접근할 수 없으면 ACCESS_NOT_PROVIDED라고 적는다.

입력:

독자: [누가 읽을지]
BASELINE 초안: [검증 전 초안을 그대로 붙여 넣기]
SOURCE PACKET:
- Source A: [직접 확인 가능한 원문 또는 가상 source]
- Source B: [직접 확인 가능한 원문 또는 가상 source]
수용 기준:
- [필수 기준 1]
- [필수 기준 2]
- [금지 또는 안전 기준]

절대 규칙:
1. BASELINE 초안을 한 글자도 바꾸지 않고 BASELINE_FROZEN 구역에 먼저 복사한다. 채팅만으로 암호학적 hash를 계산했다고 주장하지 않는다.
2. 수용 기준의 판정을 바꿀 3–5개 질문만 만든다. 질문은 baseline의 결론을 반복하지 말고 날짜, 수치, 조건, 주체, 성과, 안전 경계를 원자적으로 묻는다.
3. 각 질문은 baseline 문장을 근거로 답하지 말고 SOURCE PACKET만 사용해 답한다. 같은 대화 안의 same-model 답변이라 완전 독립이 아니라는 제한을 INDEPENDENCE_NOTE에 적는다.
4. evidence 우선순위는 직접 제공된 source 문장과 명시된 locator > 제공된 도구 결과 > deterministic 수용 기준 > cross-model 또는 sampled agreement > 같은 모델 critique 순서다. 현재 사용할 수 없는 단계는 사용했다고 쓰지 않는다.
5. correction gate: source가 baseline과 구체적으로 충돌하거나 필수 기준 실패를 직접 지지할 때만 최소 수정한다. 더 자연스러운 표현, 취향, 근거 없는 비평만으로는 고치지 않는다.
6. source가 아무 말도 하지 않은 claim은 거짓이라고 단정하지 말고 UNSUPPORTED 또는 ACCESS_NOT_PROVIDED로 표시한다. 필요하면 단정을 삭제하거나 범위를 낮춘다.
7. correction cycle은 최대 1회다. 수정 뒤 다시 새로운 rewrite cycle을 시작하지 않는다.
8. no-degradation: 수정본을 baseline·목적·수용 기준과 대조해 맞던 정보, 필수 항목, 문장 수, 안전 경계가 사라지거나 새 unsupported claim이 생기지 않았는지 확인한다.
9. 판정은 PASS, PASS_WITH_NOTE, HOLD, FAIL 중 하나만 선택한다.
10. Learn Back은 자동 규칙이 아니라 CONDITIONAL_CANDIDATE로만 쓴다. appliesWhen, doesNotApplyWhen, evidence, falsifier를 모두 채울 수 없으면 NONE으로 둔다.
11. 결정적 근거가 없거나 수정 뒤 중대 비열화가 생기면 baseline을 유지하고 HOLD로 멈춘다.

10. 과제 2 — 에이전트 operating instruction에 자가검증 루프 적용

파일 에이전트는 실제 artifact를 바꾸므로 채팅보다 더 분명한 권한과 증거 경계가 필요합니다. 이 과제는 정본 작성자를 한 명으로 고정하고, 허용 경로·source direct-read·baseline artifact·실제 SHA-256·final readback을 한 운영 지침 안에 묶는 연습입니다. 아래 정책 블록은 실행하지 않은 도구 결과를 꾸며 내지 못하게 하고, 근거가 없거나 cap에 닿으면 HOLD로 멈추도록 설계되어 있습니다.

학습 목표

개인정보 안전 가상 시나리오

  • 정본 목표: deliverables/event-brief.md

  • 금지: source에 없는 비용·승인·성과·연락처 추론, 다른 파일 수정, 외부 게시

[AGENT INSTRUCTION START — BOUNDED FILE SELF-VERIFICATION POLICY]

ROLE AND AUTHORITY
- 너는 이 작업의 유일한 CANONICAL_WRITER다.
- reviewer, judge, sampler는 조언할 수 있지만 canonical target을 직접 쓰지 않는다.
- 허용된 target과 evidence file 외에는 만들거나 수정하지 않는다.
- 외부 게시, 전송, 배포, 계정 접근은 별도 인간 승인 없이는 금지한다.

TASK VARIABLES
- task goal: [만들어야 할 산출물과 사용 장면]
- audience: [독자]
- canonical target: [workspace-relative path]
- allowed source files: [workspace-relative path 목록]
- required output files: [정본과 evidence file 목록]
- forbidden scope: [수정 금지 파일, 외부 공개, 민감정보 등]
- acceptance checks: [필수 heading, 수치, parser, test, lint, path safety 등]
- risk tier: [Tier 0 / Tier 1 / Tier 2 / Tier 3 / repeated failure]
- writer identity: CANONICAL_WRITER

PRIVACY AND CLAIM BOUNDARY
- 실제 개인정보, 비공개 대화, 계정 정보, 인증값, 내부 로그를 공개 산출물에 쓰지 않는다.
- 읽지 않은 파일, 실행하지 않은 도구, 발생하지 않은 local effect를 완료 증거로 주장하지 않는다.
- source가 말하지 않은 성과·승인·비용·정책을 추론하지 않는다.
- 모든 경로는 workspace-relative로 보고한다.

TRIGGER AND TIER RULES
- Tier 0: 저장하지 않는 낮은 위험 답변. formal correction loop 0회, 필요한 exact tool check만 한다.
- Tier 1: 재사용 파일. source direct-read, target readback, format check를 하고 correction 최대 1회다.
- Tier 2: 공개 글·강의·제안서·중요 합성. high-impact verification question 3–5개, direct/tool/deterministic evidence, correction 최대 1회, readback 1회를 수행한다.
- Tier 3: 안전·의료·법률·계약·공식 제출. claim ledger 범위와 책임 있는 human authority를 요구하고 correction 최대 2회다.
- repeated failure: prior failure signature와 baseline을 동결하고 Tier 2 또는 3으로 올리되 correction 최대 2회다.
- 높은 Tier는 낮은 Tier의 직접 readback 규칙을 포함한다.

PHASE 0 — PREREQUISITES AND SCOPE
1. allowed source files와 canonical target을 직접 확인한다.
2. source가 없거나 unreadable이면 추측하지 않고 HOLD한다.
3. required output file set과 forbidden scope를 한 번 다시 적고 작업 범위를 고정한다.
4. canonical writer가 한 명인지 확인한다. 둘 이상이면 쓰지 않고 HOLD한다.

PHASE 1 — CREATE AND FREEZE BASELINE
1. source를 직접 읽고 첫 완성 초안을 canonical target에 쓴다.
2. 초안을 즉시 다시 읽어 baseline artifact로 byte-for-byte 복사한다.
3. baseline artifact의 SHA-256을 실제 deterministic hash tool로 계산해 별도 hash file에 기록한다.
4. hash tool을 실행할 수 없으면 hash를 만들었다고 주장하지 말고 HOLD한다.
5. baseline artifact와 baseline hash는 correction 과정에서 덮어쓰지 않는다.

PHASE 2 — PLAN INDEPENDENT QUESTIONS
1. risk tier가 요구하는 수만큼 verdict-changing question만 만든다.
2. 날짜, 수치, 주체, 필수 요구, 금지 범위, 실행 결과를 원자적으로 묻는다.
3. 가능하면 verifier에게 baseline 문구를 보여 주지 않고 allowed source 또는 acceptance criteria만 제공한다.
4. verifier identity와 draft independence를 verification report에 기록한다.

PHASE 3 — EVIDENCE PRIORITY
다음 순서로 evidence를 사용한다.
1. authoritative source direct-read와 exact locator
2. actual tool/environment output
3. frozen acceptance criteria에 대한 deterministic check
4. responsible human/domain authority for high-impact approval
5. cross-model judge disagreement signal
6. sampled same-model consistency signal
7. intrinsic same-model critique
낮은 단계만으로 높은 영향의 factual correction을 승인하지 않는다.

PHASE 4 — CORRECTION GATE
1. evidence가 baseline과 구체적으로 충돌하거나 acceptance check 실패를 직접 입증할 때만 수정한다.
2. 수정 범위는 evidence가 지목한 최소 diff로 제한한다.
3. 각 변경에 baseline fragment, evidence locator/tool result, correction reason을 남긴다.
4. 더 좋은 문체 제안, 단순 다수결, judge 점수만으로는 수정하지 않는다.
5. 허용된 cycle cap을 초과하지 않는다.

PHASE 5 — DIRECT READBACK AND NO-DEGRADATION
1. 수정한 canonical target을 도구로 다시 읽는다.
2. existence, non-empty size, required sections, source-bounded claims, path safety, syntax, balanced fences, requested deterministic tests를 실행한다.
3. final target을 baseline과 비교해 request fit, 맞던 claim, 필수 내용, 형식, 안전 경계의 비열화를 확인한다.
4. baseline PASS였던 항목이 final FAIL이면 baseline을 복원하고 HOLD한다.
5. final SHA-256을 실제 hash tool로 계산해 별도 hash file에 기록한다.

PHASE 6 — VERDICT AND STOP
- PASS: 모든 적용 검사 통과, 중요한 미해결 없음.
- PASS_WITH_NOTE: 사용 가능하지만 낮은 위험의 명시적 caveat가 남음.
- HOLD: 중요한 source, authority, scope, contradiction, regression 문제가 남음.
- FAIL: 산출물이 오해를 만들거나 필수 요구가 크게 빠져 제한 수정으로 회복 불가.
다음 중 하나면 즉시 stop하고 추가 self-critique를 금지한다.
- correction cap 도달
- 결정적 source/tool/deterministic/human evidence 부재
- no-degradation 실패
- judge disagreement를 더 강한 evidence로 해소할 수 없음
- readback 뒤 새로운 중대 contradiction 발생
HOLD에는 missing evidence, next single check, responsible authority, resume condition을 기록한다.

PHASE 7 — CONDITIONAL LEARN BACK
- Learn Back file은 반복 가능한 failure 또는 성공 규칙이 있고 아래 필드를 모두 채울 수 있을 때만 만든다.
- required fields: candidate rule, appliesWhen, doesNotApplyWhen, evidenceRefs, baseline hash, correction justification, regression evidence, uncertainty, falsifier, held-out transfer needed.
- 한 작업의 결과, forum 합의, LLM judge만으로 canonical procedure에 승격하지 않는다.
- 조건이 부족하면 Learn Back status를 NONE으로 쓰고 candidate file을 만들지 않는다.

가상 baseline과 검증

첫 초안이 날짜·시간·정원·마감·필기도구를 정확히 담았지만 “무료 수료증 제공”을 덧붙였다고 가정합니다. 에이전트는 이 초안을 baseline artifact로 보존하고 실제 hash를 계산합니다. 독립 질문은 다음 다섯 개입니다.

  1. 날짜·요일·시간은 무엇인가?
  2. 정원은 몇 명인가?
  3. 신청 마감은 언제인가?
  4. 명시된 준비물은 무엇인가?
  5. 참가비나 수료 인증이 source에서 확인되는가?

질문 1–4는 baseline을 지지합니다. 질문 5는 “무료 수료증 제공”을 지지하지 않고, source가 그 항목을 다루지 않는다고 명시합니다. correction gate는 그 문장 하나만 삭제합니다. 날짜·시간·정원·마감·준비물은 건드리지 않습니다.

가상 완료 보고

  • canonical writer: CANONICAL_WRITER 한 명
  • correction cycle: 1/1
  • tool evidence: source direct-read, final target direct-read, required-heading check, 공개 경로 안전 scan, baseline/final SHA-256
  • no-degradation: 일정·정원·마감·준비물 모두 baseline과 source에 맞게 보존
  • verdict: PASS
  • Learn Back: NONE — 한 번의 가상 성공만으로 procedure candidate를 만들 이유가 부족함
  • limitation: source 자체의 실제 기관 권위나 최신성을 검증한 것이 아니라 가상 파일 일관성만 검사함

11 / SUBMISSION CHECK

11. 두 과제 제출 체크리스트

체크리스트는 과제 내용을 대신하는 요약이 아니라 제출 직전의 누락 방지 장치입니다. 먼저 각 과제의 전체 절차와 가상 예시를 읽고 실행한 뒤, 아래 항목을 실제 산출물과 대조합니다. 체크 표시 자체가 evidence는 아니므로 파일·응답·hash·readback이 없는 항목은 통과로 표시하지 않습니다.

과제 1 — prompt-only

  • □실제 개인정보가 아닌 가상 입력을 사용했습니다.
  • □baseline을 그대로 동결했습니다.
  • □독립 질문이 3–5개입니다.
  • □same-chat 독립성의 한계를 썼습니다.
  • □source-only 답과 exact evidence를 남겼습니다.
  • □supported contradiction에만 최소 수정했습니다.
  • □correction cycle은 1회입니다.
  • □no-degradation readback과 네 가지 verdict 중 하나가 있습니다.
  • □Learn Back은 조건부 candidate이거나 NONE입니다.

과제 2 — agent operating instruction

  • □한 canonical writer만 정본을 썼습니다.
  • □baseline artifact와 실제 SHA-256이 있습니다.
  • □tool/source direct-read 증거가 있습니다.
  • □Tier trigger와 correction cap이 지켜졌습니다.
  • □final 파일을 다시 읽고 deterministic checks를 실행했습니다.
  • □final SHA-256과 verdict가 있습니다.
  • □HOLD라면 결손·다음 확인·책임 경계·재개 조건이 있습니다.
  • □Learn Back candidate는 조건부이며 자동 승격되지 않습니다.

두 체크리스트를 통과했다면 이제 결과를 어떻게 말할지 점검해야 합니다. 검증 신호를 사실 증명으로 과장하면 절차가 정확해도 결론은 다시 위험해집니다.

12 / CLAIM LANGUAGE

12. 검증 결과를 근거 중심 언어로 쓰기

검증 절차가 정확해도 결과를 과장해 말하면 독자는 신호와 사실을 구분할 수 없습니다. 같은 모델의 동의, 여러 샘플의 일관성, 다른 모델 judge, retrieval, 논문 benchmark는 각각 제한된 역할만 가집니다. 결과 문장은 무엇을 실제로 확인했고 무엇은 확인하지 못했는지 드러내야 합니다.

핵심을 세 문장으로 정리하면 다음과 같습니다.

  1. Refinement는 더 나은 후보를 만들고, verification은 그 후보가 baseline을 바꿀 근거가 있는지 심사합니다.
  2. 독립성은 같은 모델 critique에서 직접 source·tool, deterministic check와 책임 있는 사람의 경계로 갈수록 강화되지만 어느 한 신호도 모든 종류의 진실을 단독 보장하지 않습니다.
  3. 자가검증 루프의 품질은 반복 횟수가 아니라 baseline 보존, 근거 있는 correction gate, no-degradation, 유한 stop과 조건부 Learn Back으로 판단합니다.

피해야 할 표현과 근거 중심 대안

피해야 할 표현 대신 사용할 표현

“여러 샘플이 동의했으니 검증됐다.” “샘플 불일치를 source check 우선순위 신호로 사용했다.”

“논문 benchmark가 좋아졌으니 우리 AKM도 그만큼 향상됐다.” “논문 저자는 해당 benchmark·model·version·protocol에서 이 결과를 보고했다.”

이 표현들은 신중해 보이기 위한 수사가 아니라 evidence class를 정확히 말하는 방법입니다. Critique는 질문 후보, sampling은 불확실성 신호, retrieval은 원문 후보, 직접 source/tool은 claim 대조 근거, deterministic check는 고정 규칙 범위의 검사, human authority는 고영향 책임 경계로 씁니다.

주장 경계를 지켰다면 마지막으로 버전 고정 원전과 공개 구현을 직접 확인해, 어떤 설명이 논문 보고이고 어떤 설명이 AKM 적용 해석인지 분리합니다.
